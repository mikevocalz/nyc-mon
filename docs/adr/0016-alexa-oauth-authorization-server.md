# 0016 — Alexa+ authorization server: upstream oauth-provider, OAuth only

- **Status:** Accepted
- **Date:** 2026-10-08
- **Deciders:** Mike (creator) through the lead; lane B implements
- **Supersedes:** the OIDC-provider plan in ADR 0006 (Decision 6 and the second Consequence). The rest of ADR 0006 stands.
- **Sources:** `docs/alexa/PLATFORM-DOCS.md` §2.3–2.5 and §3.3, ADR 0015 §1, `docs/alexa/AUTH.md`
- **Code:** `packages/payload/src/auth/oauth/`, `apps/admin-vite/src/routes/oauth/*`, `apps/admin-vite/src/routes/[.]well-known/oauth-authorization-server.ts`, migration `20261008_181202_alexa_oauth`

## Context

ADR 0006 assumed Better Auth's OIDC-provider plugin would be the authorization server. Amazon's Alexa+ add-on docs rule that out: OpenID Connect, dynamic client registration and client ID metadata documents are all "not supported yet". What Amazon does require:

- `client_credentials` with scope `mcp:service` for `initialize` and `tools/list`;
- `authorization_code` with PKCE S256 for user tools, and a refresh token with every access token;
- HTTP Basic client auth at the token endpoint, no credentials in query strings;
- static client registration, with Alexa's redirect URIs printed by its CLI;
- RFC 8414 metadata at `/.well-known/oauth-authorization-server`;
- `resource` validated against the registered MCP URI.

The pinned better-auth 1.7.7 ships no authorization-server plugin. Its `dist/plugins` has `jwt` but no `oidc-provider` or `mcp` plugin. The provider now lives in a separate package, `@better-auth/oauth-provider`, released at 1.7.7 alongside better-auth.

## Decision

1. **Use `@better-auth/oauth-provider@1.7.7` (`oauthProvider`) with better-auth's `jwt` plugin.** Both are pinned through the pnpm catalog. Token, PKCE, rotation and client-authentication code stays upstream, keeps Better Auth's per-endpoint rate limits, and the linking flow signs in through Better Auth itself (password plus TOTP today; passkey is not wired into the linking page yet).
2. **OAuth only, no OIDC.** `scopes` omits `openid`, so the provider serves RFC 8414 metadata, `/.well-known/openid-configuration` answers 404, and no ID token is minted. `/oauth2/userinfo` and `/oauth2/end-session` are in `disabledPaths`.
3. **The issuer is the admin-vite origin** (`AUTH_ISSUER`, else the `BETTER_AUTH_URL` origin), set as the `jwt` plugin's `jwt.issuer`. admin-vite serves the metadata at the root `/.well-known/oauth-authorization-server` through the provider's `oauthProviderAuthServerMetadata`. The endpoints themselves stay under `/payload-api/auth/oauth2/*`.
4. **Two static clients from env.** `alexa` (confidential, `client_secret_basic`, all three grants) and `nyc-mon-sim` (public unless `OAUTH_SIM_CLIENT_SECRET` is set). The provider's admin endpoint always generates its own client_id, so a small plugin (`clients.ts`) upserts the rows and their resource links at boot. Client CRUD, DCR and resource CRUD are closed: `clientPrivileges` and `resourcePrivileges` return false, and the HTTP paths are disabled.
5. **One resource, `MCP_RESOURCE_URI`**, seeded by the provider with `enforcePerClientResources: true`. A guard (`guards.ts`) makes `resource` mandatory on the authorization request and on the code and client-credentials grants, because without it the provider issues an opaque token with no `aud`.
6. **Refresh tokens always.** The provider issues one only for `offline_access`, so the guard adds that scope to every user authorization request. Rotation and reuse detection are the provider's: a reused refresh token revokes the family.
7. **18+ at three points**, using `birthYear` and `consentStatus` from the Users collection (ADR 0015 §1). A year that could belong to someone 17 is refused, as is any account that went through guardian consent.
   - `postLogin.shouldRedirect` sends a refused account to `/oauth/refused` before consent.
   - A `hooks.before` guard on `/oauth2/consent` and `/oauth2/continue` refuses `accept: true` from a refused account.
   - `customAccessTokenClaims` throws `invalid_grant` for a refused user on every code exchange and refresh. This is the layer that cannot be skipped.
8. **Scopes:** `mcp:service` (client credentials only), `mcp:caller`, `mcp:care`, plus `offline_access`. The MCP server checks them; the contract is in `docs/alexa/AUTH.md`.

## Consequences

- Eight new Payload collections (`jwks` and seven `oauth_*`), generated by `betterAuthCollections` and created by migration `20261008_181202_alexa_oauth`. The migration has not been applied to any database.
- If the migration is missing, the client seed logs an error and linking fails; the admin console still boots.
- Alexa caches the metadata at deploy time. Any change to the issuer, scopes or endpoints needs `alexa-ai deploy` again.
- The linking page's sign-in supports email and password with TOTP. Passkey and Apple/Google sign-in on that page are open work.
- Not verified against Amazon: whether its token request passes Better Auth's origin and CSRF checks from a server with no `Origin` header. The tests drive the handler directly.
