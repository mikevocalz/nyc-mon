# Valdrada lane frame cost — Surface Duo, 2026-10-18

Companion to `worklet-ab-2026-10-17.md` (R1), `gpu-budget-2026-10-17.md` (G1)
and `baseline-duo-2026-10-17.md` (M0). Same device (Surface Duo 1,
2700×1800, ~60 Hz), release builds, `EXPO_PUBLIC_GAME_PERF=1`, measured while
walking 125th Street under `EXPO_PUBLIC_WORLD_VD=1`.

## The finding, up front

**The VD scene costs p50 ~27 ms of CPU encode plus ~9 ms present on the
worklet path. 60 fps is not reachable on this device with the current
material stack.** GPU p50 is 4–5 ms — the device has shader headroom; the
wall is CPU-side command encoding through the TSL node-material graph plus
the swapchain present, and the Android UI thread ceiling from U1 still sits
underneath both render paths.

Per-config medians, release, walking:

| Config | Frame p50 | encode p50 | present p50 | fps |
| --- | --- | --- | --- | --- |
| JS path, VD, shadows off, scale ~0.53 | ~23 ms | 19.6 ms | ~0.4 ms | ~30 |
| JS path, VD, shadows on | ~32 ms | ~28 ms | — | ~31 |
| JS path, `WORLD_TIER=high` + BUNDLES | ~36 ms | 28.4 ms | 9.3 ms | ~22 |
| Worklet + `WORKLET_VSYNC`, VD | 38.6 ms | 26.8 ms | 9.3 ms | ~26 |

Common across all four: `update()` p50 ~0.2 ms, ~81 draw calls,
`trianglesP50` ~1.14 M.

## Where the triangles are

Trees own ~92% of the frame. `VD_NEAR_TREE_CAP` 48 full models (~19k
triangles each after instancing costs) plus `VD_MID_TREE_CAP` 160 card-tree
mids (~0.9k each) is ~1.05 M of the 1.14 M; the whole merged city — facades,
street furniture, props — is ~0.1 M. The caps were already halved once this
lane (90/330 → 48/160 cut 2.0 M → 1.14 M, frame p50 62 → 32 ms).

Halving again (24/80) projects encode ~15–17 ms — still over budget before
the ~9 ms present, and the visible cost is real: nearest-24 full trees means
card crowns inside ~30 m on a tree-lined Harlem block. A far-card imposter
tier (like `tree-lod.ts`'s crown system for the old city) is the structurally
right cut: it keeps the canopy silhouette while pushing visible triangles
toward ~300 k.

## `WORLD_BUNDLES` freezes the camera — do not ship it with a moving camera

The "parked aerial" bug reported this lane was never a placement failure.
`placeCaller` fired correctly and every draw rendered the chase pose
(distance 8, y ≈ 4.1 m); the visible frame still showed the 220 m overview.
`BundleGroup` records the camera-dependent contents at record time — the
first (220 m reveal) frame — and replays them every draw. The bundle painted
the frozen aerial over every correct subsequent frame; with the flag off the
Caller lands at street level and the chase camera tracks.

A second defect on the same flag: tree leaf textures render unbound during
bundle replay (canopies solid white).

`EXPO_PUBLIC_WORLD_BUNDLES` was deleted outright on `lane-bundlefix`
(2026-11) — an opt-in flag that can never ship on a moving-camera build is
dead weight, and re-record-on-move forfeits the encode win it exists for.
Until `BundleGroup` re-derives camera state per replay or bundles are
restricted to camera-independent content, it buys nothing measurable anyway:
the high-tier bundle run above was the *worst* of the four configs.

## What the worklet path did and did not buy

`WORKLET_RENDER=1` + `WORKLET_VSYNC=1` works and is stable — native frame
callback pacing, no timer poll, idle parking confirmed in logcat. But encode
moved with the scene code: 26.8 ms p50 on the render runtime vs ~28 on JS
(shadows on for both). Moving threads removed the JS-thread contention U1
documented and got ~nothing back, because the encode itself is the cost.
That matches R1's conclusion on the lighter scene: pacing was the fixable
part; per-draw CPU cost is what's left.

## Update: far-card imposter tier (dc5d63c), same evening

Trees past 140 m of the focus (or past the mid cap) now draw as per-species
cross-card imposters — two leaf-atlas quads plus a trunk cross, 8 triangles a
tree — selected by a pure `VdTreeTiers` class in the `TreeLod` mould.
Duo, release, VD + shadows off + living city, walking:

| | Before | After |
| --- | --- | --- |
| trianglesP50 | 1,146,000 | **580,000** |
| render encode p50 | 19.6 ms | **13.5 ms** |
| cpuP50 | 22.9 ms | **15.5 ms** |
| cpuP90 | — | 25.9 ms |

**The median frame is now inside the 16.7 ms budget.** The remaining jank is
the tail: `present` p90 ~11 ms (swapchain back-pressure against the composed
window) plus the U1 UI-thread ceiling. 60 fps sustained needs that tail, not
more encode work.

## Update: merged tier draw calls (a0281e9), same night

The six per-species mid trunks, far trunks and far cross-cards collapse to
three shared `InstancedMesh`es (36 vd meshes → 21): one trunk material serves
both merged tiers, the far geometries normalise to unit boxes with the
species crown folded into the instance matrix, and the atlas layer plus card
tiling move to instanced `aLayer`/`aRep` attributes. Duo, release, same
config, walking:

| | Imposter tier | Merged draws |
| --- | --- | --- |
| drawCallsP50 | 83–85 | **72** |
| renderP50 | 12.5–13.5 ms | **11.4 ms** |
| renderP90 | 14.9–16.7 ms | **13.8 ms** |
| cpuP50 | 15.5–16.1 ms | 17.7 ms* |
| trianglesP50 | ~580k | 577k |

*cpuP50 rose in this window because `present` p90 hit 20.3 ms — the tail is
noisy across windows (4.8 ms p50, 20.3 ms p90 here). Encode, the part this
change targets, improved at both percentiles. Far imposters verified
rendering on-device at street and corridor distance.

The wall is now unambiguous: `present` p90 ~16–20 ms of swapchain
back-pressure at a 1080–1275 px-wide buffer on the 2700×1800 panel — the
SurfaceFlinger GPU-deadline / Buffer-Stuffing misses U1 already attributed.
The render-scale controller holds at the 0.5 floor inside the phone band
[27,38]; a lower floor is a product call.

## Honest paths to 60, in effort order

1. ~~Far-card tree imposters~~ — **shipped, dc5d63c** (see update above).
2. A cheaper material tier for mid/far geometry (unlit or baked-look instead
   of full TSL graphs) — the encode cost tracks node-graph evaluation, not
   just triangle count.
3. The UI-thread side from U1 still applies whichever thread draws: the
   composed window with active Rive controls ran 38–44 ms per frame in that
   investigation. Parking helped; consolidation has not been done.
4. Shadows stay off on this device class (`WORLD_VD_SHADOWS=0` saved ~8 ms
   of encode).

Even 1+2+3 together land ~14–18 ms — 60 fps on the Duo is a stretch goal
against the compositor, not a config flag away.

## Reproduce

```sh
rm -f app/build/generated/assets/react/mobileRelease/index.android.bundle*
EXPO_PUBLIC_WORLD_VD=1 EXPO_PUBLIC_WORKLET_RENDER=1 EXPO_PUBLIC_WORKLET_VSYNC=1 \
EXPO_PUBLIC_GAME_PERF=1 ./gradlew :app:assembleMobileRelease
adb -s 913949703467 install -r app/build/outputs/apk/mobile/release/app-mobile-release.apk
adb -s 913949703467 shell am start -a android.intent.action.VIEW -d "nycmon:///game" com.nycmon.app
# walk for ~60 s via on-screen stick (argent drag hold)
adb -s 913949703467 shell dumpsys gfxinfo com.nycmon.app framestats
adb -s 913949703467 logcat -d | grep 'NYC-Mon/perf'
```

The `worklet render submission` probe lines carry the stage breakdown
(`renderP50Ms`, `presentP50Ms`, `drawCallsP50`, `trianglesP50`, `bufferW/H`).
