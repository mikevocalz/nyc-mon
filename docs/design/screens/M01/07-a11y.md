# M01 Boot / power-on: accessibility

Owner: `a11y-auditor`. Standard: WCAG 2.2 AA (https://www.w3.org/TR/WCAG22/), Apple HIG accessibility (https://developer.apple.com/design/human-interface-guidelines/accessibility), Android accessibility (https://developer.android.com/guide/topics/ui/accessibility). Inputs: `03-direction.md`, `04-components.md`, `05-copy.md`, `06-critique.md`, `docs/design/hlynk/DIRECTION.md`, `docs/DESIGN_SYSTEM.md`, `docs/COPY_DECK.md`. Stage: design. Nothing is built, so every row below is a requirement, not a test result.

**Verdict:** likely accessible foundation. One timing risk (the boot window swallowing a screen reader's first focus) and one flash-safety check carry into the handoff.

## Focus order

Boot lasts at most 600 ms and nothing on it is operable. The order below is what a screen reader or keyboard meets if it lands during that window.

1. The scanner head (`ScannerLed`), role `image`, label from `hlynk.led.a11y` once a state exists; during `boot` it is hidden from accessibility (decorative ramp).
2. Keys and trackpad, row order: Home, Menu, Trackpad, Back, Forward. All disabled; each still exposes its name so a user who swipes into the row hears what it is.

After `power` reaches `on`, focus does **not** stay on the shell. It moves to the destination's `Heading level={1}` (M02 first panel on a first run, M11 or M13 when returning). On first run the shell lowers away and is removed from the accessibility tree before M02 takes focus, so VoiceOver never reads controls that are leaving.

Risk to verify on device: iOS may put initial VoiceOver focus on the first element of the boot frame and then lose it when the route swaps. Platform sets focus explicitly on the destination heading (`AccessibilityInfo.setAccessibilityFocus` on native, `focus()` on the `h1` with `tabIndex={-1}` on web) after the swap.

## Reduced motion map

Gated once by the sim-core adapter (`AccessibilityInfo.isReduceMotionEnabled` on native, `prefers-reduced-motion` on web), passed down as `reducedMotion`. Components never read the OS themselves (§3.6).

| Motion | Full | Reduced (authored sibling) |
|---|---|---|
| LED power-on (`motion-power-on`) | ramp 0 → 100% over 240 ms | steps straight to 100% at 0 ms |
| Scanner fan (`motion-scan-fan`) | one upward sweep, 400 ms, inside the head | absent |
| Trackpad ring | `apple-900` → `apple-500` across 240 ms | steps to `apple-500` at 240 ms |
| Screen | fades 0 → 1, 240–600 ms | cuts on at 240 ms |
| Shell body | scale 0.98 → 1 | no scale |
| First-run shell lowering | `motion-enter` reversed, 300 ms | 200 ms cross-fade |
| LED settle on destination | rhythm per state (`DIRECTION.md`) | steady light plus shape cue (tick row, filled dot, exclamation dot) |

Copy does not change in either mode (`05-copy.md`). The power-on announcement fires at 240 ms in both.

**Flash safety (WCAG 2.3.1).** M01 itself has no blink: the boot ramp is one rise. The states it settles into do blink: `ready` is two 150 ms blinks and `needsYou` is three 150 ms blinks. Three flashes inside 750 ms sits exactly at the "no more than three in any one second" limit, and the light is saturated red, which 2.3.1's red-flash clause singles out. The lens is far smaller than the 0.006 sr area threshold on any phone, so it passes, but M13's handoff must not lengthen the burst or enlarge the lens without re-checking.

## Dynamic Type

No text on the boot frame, so nothing scales. The control row is sized in points, not by font scale, and must not grow with Dynamic Type (it would break the SE height budget of 139 pt). The keys' accessible names carry the meaning for users who need larger text. The destination's chip (`type-caption`) is checked on M11 and M13.

Large Content Viewer (iOS): each `HLynkKey` sets `accessibilityShowsLargeContentViewer` with its label, so a user at accessibility sizes who long-presses a glyph-only key sees its name enlarged. This matches the long-press tooltip in `DIRECTION.md`.

## Responsive and foldable

Width classes follow Material 3 (https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes), already encoded in `apps/mobile/src/navigation/split-view/constants.ts`: compact < 600 dp, medium 600–839, expanded 840–1199, extra-large ≥ 1200.

| Width class / posture | Behaviour |
|---|---|
| Compact, portrait (phones) | Standard `HLynkShell` layout. SE 3 is the tight case (139 pt for the row; fits per `DIRECTION.md`) |
| Compact, short height (landscape, slide-over) | `layout="compact"`: full-bleed screen, 24 pt head strip, 72 pt bar. Phase 1 phones are portrait-only, so this mainly covers iPad slide-over |
| Medium / expanded / extra-large | The shell renders at phone proportions, centred, at most 440 pt wide, on the scheme's page colour. It never stretches to tablet width, because the 3:4 screen and 112 pt pad are the object |
| Foldable, book posture (vertical hinge) | The whole shell sits in one pane (the leading pane). The hinge never crosses the shell |
| Foldable, tabletop posture (horizontal hinge) | `HLynkScreen` above the hinge, the scanner head with it; the control row below. The row is one control group and never straddles the hinge |
| Hinge occlusion | Read from the adaptive-panes reserved regions (`@acme/ui/adaptive-panes`, being ported; `docs/DEVICE_CHECKS.md` "Adaptive panes + fold module") |

The tabletop split is a proposal from this audit. It keeps every control group whole; `design-director` confirms it in M08's direction, where the shell first becomes interactive.

## Keyboard (web)

The Expo web build runs `/` too.

| Element | Tab | Enter / Space | Escape | Arrows |
|---|---|---|---|---|
| Keys, trackpad during boot | focusable with `aria-disabled="true"` so a keyboard user can discover them; no action | nothing | nothing | nothing |
| After power-on | focus moves to the destination `h1` (`tabIndex={-1}`) | — | — | — |

No focus trap, no auto-advance a keyboard user must outrun: boot is 600 ms and needs no input. `prefers-reduced-motion` selects the reduced column above. The page has one `<main>`; the shell is `<figure aria-hidden="true">` on first run so it does not add a landmark that disappears.

## Findings

| # | Issue | WCAG | Severity | Fix |
|---|---|---|---|---|
| 1 | Initial screen-reader focus can land on boot controls that vanish at 600 ms | 2.4.3 Focus Order | High | Explicit focus to the destination `h1` after the route swap; boot shell hidden from AT on first run |
| 2 | `needsYou` blink burst sits at the 3-flash limit | 2.3.1 | Low | Keep 150 ms on / 150 ms off and three blinks maximum; re-check if M13 changes the LED |
| 3 | Glyph-only keys need their names at large text sizes | 1.1.1, 2.5.3 | Medium | Accessible names from `hlynk.key.*`; Large Content Viewer on iOS; tooltip on long-press |
| 4 | Power-on announcement could talk over the destination title | 4.1.3 Status Messages | Medium | Polite, not assertive; fires at 240 ms, before the destination announces |
