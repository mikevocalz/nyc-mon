# Ops console: research

Owner: `design-director`. Written 2026-10-04. Surface: the NYC-MON Payload admin at `/admin` on `apps/admin-vite` (ADR 0003), replaced end to end by a custom console built from `@acme/ui` (LAWS R3). Inputs: `prompts/LAWS.md`, ADR 0001 (auth, age and consent), ADR 0003 (admin app split), `docs/canon/DECISIONS.md` #2, #3, #4, #11, #15, `packages/payload/src/collections/Users.ts`, `packages/core/schemas/*`, `@acme/content`.

## Status: proto-personas

Nobody has watched staff use this console; it does not exist yet. The people below come from the jobs ADR 0001 and the build prompt create (consent, deletion, hatch integrity, content), not from interviews. Claims are marked:

- **Repo:** read from a file in this repo, with its path.
- **Law / canon:** from `prompts/LAWS.md` or `docs/canon/DECISIONS.md`.
- **Regulation:** COPPA, 16 CFR Part 312 (https://www.ecfr.gov/current/title-16/chapter-I/subchapter-C/part-312) and the FTC COPPA FAQ (https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions).
- *(assumption)*: unverified; each one is a question for the first walkthrough with Mike.

## Who uses it

Phase 1 staff is small. One person may hold several roles, so the console is built around jobs, and each role is a permission set, not a separate app.

| Person | Role | How often | Device | Main pull |
|---|---|---|---|---|
| Mike | ops (owner) | daily | laptop, phone between meetings *(assumption)* | Is anything broken? Did any hatch duplicate a Mon? |
| Support agent | support | daily when live | laptop | Find one Caller fast, answer "where is my Mon?", start a deletion |
| COPPA consent reviewer | consent | weekly, plus on alert | laptop | Pending and expiring guardian consents, parent requests, deletion proof |
| Content editor | content | per content drop | laptop or tablet | Check what `@acme/content` shipped: Bloodlines, forms, eggs, open `TODO(canon)` gaps |

Today `users.role` has two values, `user` and `admin` (repo: `packages/payload/src/collections/Users.ts`), and the plugin's `hasAdminRoles()` gates the admin. There are no staff roles. See "Blockers" below.

## Jobs to be done

- **Mike (ops):** When I open the console, I want to see in one screen whether any hatch broke Law 6 and whether the consent queue is backing up, so I only dig when something is wrong.
- **Mike (ops):** When a duplicated individual shows up, I want the egg, both instances, the Caller and the request trail in one place, so I can fix it before the Caller notices two Mons.
- **Support:** When a Caller writes in "my Mon is gone after I got a new phone", I want to find them by email or Caller id and see their Mons and last sync, so I can tell them the Mon is safe (canon: "A device session is a surface, not a new creature", ADR 0001).
- **Support:** When a Caller asks to delete their account, I want to start the deletion with the 7-day grace (BUILD_PROMPT_v3 §M20) and tell them the date it completes, so nothing is deleted by accident and nothing lingers.
- **Consent reviewer:** When a guardian consent is pending, I want to see when it expires and what has been sent, without seeing more of the child than the law lets us hold, so I can chase or let it lapse.
- **Consent reviewer:** When a parent asks to see or delete what we hold about their child (16 CFR 312.6), I want one place that lists every record tied to that consent and a deletion that leaves proof, so I can answer within the deadline counsel sets.
- **Content editor:** When a content drop lands, I want to see each Bloodline's tree, every egg and which fields are still `TODO(canon)`, so I can tell Mike what is missing before a screen ships it.

## What the console touches (data inventory)

| Data | Where it lives | Exists today? | Sensitivity |
|---|---|---|---|
| Caller account: email, name, image, `birthYear`, `consentStatus`, `role`, `emailVerified` | `users` (repo) | yes | personal data; a 13–17 Caller is a minor |
| Sessions, accounts (OAuth tokens), verification tokens, passkeys | Better Auth collections generated by `betterAuthCollections` (repo: `payload.config.ts`) | yes | secrets; never rendered |
| Guardian consent: `parentEmail`, `birthYear`, `status`, `expiresAt` | `guardian-consents` (ADR 0001, "Age and consent") | **no** | parent's personal data, held only to seek consent (312.5(c)(1)) |
| Eggs: `eggId`, reserved `monInstanceId`, species, `incubationEndsAt`, hatched flag | `eggs` (ADR 0001, `/v1` table) | **no** | game state |
| Mon instances: `monInstanceId`, `eggId`, `speciesId`, nickname, `callerId`, `hatchedAt`, bond, stage | `mon-instances` (ADR 0001); shape is `MonInstanceSchema` (`packages/core/schemas/mon.ts`) | **no** | game state; nickname is Caller-authored text |
| Care state per Mon, `lastAppliedSeq` | `CareStateSchema` (`packages/core/schemas/care.ts`); server table not named | **no** | game state |
| Audit trail | nothing | **no** | staff actions; must not copy personal data into it |
| Bloodlines, forms, eggs | `@acme/content` (`packages/content/index.ts`, `eggs.ts`, `mons/*`) | yes, code | public canon; read-only in the console |

Only `users` and `media` exist as hand-written collections (repo: `packages/payload/src/payload.config.ts`). Half of the console reads data no collection holds yet.

## Risks

### 1. Exposing a minor's data (highest)

- An under-13 child never has an account. ADR 0001: "no Better Auth account is created and no child email, Apple or Google identity is collected." The console must not invent a place to type one in. A free-text "notes" field on a consent record is the most likely way a child's name ends up in our database. **No free-text fields on consent records.**
- 13–17 Callers have accounts and are minors. Not COPPA-covered, but the same care applies: their email, name and exact birth year show only to a role that needs them, and a reveal is logged.
- Birth year alone identifies an age band. The list shows the band ("Under 13", "13 to 17", "18 and over"), never the year. The detail view reveals the year on request, logged.
- Screenshots and shoulder-surfing: support works from laptops in shared spaces *(assumption)*. Masked by default, revealed per field, re-masked on navigation.
- The plugin's generated collections hold OAuth tokens and session tokens. Stock Payload would list them in the nav (ADR 0003, "Verified": the dashboard lists Sessions, Accounts, Verifications, Passkeys). The console hides them and never renders a token value.

### 2. Deletion

- **Guardian consent denied or expired:** the parent email and the record are deleted (ADR 0001; 312.5(c)(1)). Decision #15: the Mon stays with Dr. Santoro in the story and is never shown as deleted or turned back into an egg (Law 8). The console shows the consent outcome and the deletion receipt; it never offers "delete the Mon".
- **Account deletion:** two steps with a 7-day grace (BUILD_PROMPT_v3 M20). ADR 0001 "Consequences": deletion removes the `users` row, its sessions, accounts and passkeys, and the Caller's Mons after the grace period. Staff can start it on a Caller's written request, cancel it inside the grace, and see the scheduled completion date. Staff cannot skip the grace from the console *(product decision, recorded in 03-direction.md)*.
- **No bulk delete.** Bulk actions in this console are limited to non-destructive ones (export a selection's ids, resend a consent email).
- Deletion must leave a receipt that proves it happened without keeping what was deleted: actor, time, record type, record id, reason code. No email, no name.

### 3. Audit trail

- Every staff read of masked data, every state change, every deletion and every role change writes one audit event, inside the same transaction as the change (Payload: pass `req` to nested operations; payload skill, "Transaction Failures in Hooks").
- Append-only: no role may update or delete an audit event, the owner included.
- The audit log is itself a privacy risk. It stores ids and reason codes, never the revealed value.

### 4. Hatch integrity (P0)

- Law 6: one `monInstanceId` per egg; a duplicated individual is a P0. The server has unique indexes on `eggs.eggId` and `mon-instances.eggId` as the backstop (ADR 0001). The console's job is detection and evidence, not repair: it must make a duplicate impossible to miss and impossible to "fix" with a click that deletes a Mon (Law 8).
- Checks the console can run read-only:
  - more than one `mon-instances` row for an `eggId` (should be impossible with the index; if it ever shows, the index is missing or was bypassed);
  - an instance whose id is not `UUIDv5(NYC_MON_NAMESPACE, callerId + ":" + eggId)` (ADR 0001, "Idempotent hatch and offline play");
  - an egg marked hatched with no instance, or an instance whose egg is not marked hatched;
  - eggs past `incubationEndsAt` for a long time and not hatched (stuck, not broken; informational).

### 5. Stock Payload leaking through

- Mike's rule: the admin is custom, built from NYC-Tron. Any route that still renders Payload's own list, edit, account or login view breaks it. The plugin also sets `views.login` and `logout.Button` itself (repo comment in `packages/payload/src/admin/components.ts`). Every reachable admin route needs an owner in `04-components.md`.

### 6. Language

- Law 9 holds in staff UI too: `Caller`, never "user" or "player"; `Bloodline`, never "family"; `H-Lynk`, never "device"; `Hood Mon`, never "wild". The Payload collection slug `users` stays a slug; the label shown is "Callers". Staff accounts are "Staff".

## Usability questions

1. Can Mike tell from the Overview, without scrolling on a phone, whether any hatch is broken?
2. Can support find a Caller by email in one search and read their Mons without revealing anything masked?
3. Does the consent reviewer understand which consents expire this week without opening each one?
4. Does anyone try to delete a Mon? If yes, the copy around Decision #15 needs work.
5. On a phone, can support finish "start deletion" with one thumb and no horizontal scroll?

## Blockers found during research

| # | Blocker | Owner | Effect on the console |
|---|---|---|---|
| B1 | `guardian-consents`, `eggs`, `mon-instances`, care state and `audit-events` collections do not exist | `platform` | Consent queue, Mons/Eggs, Audit log and the Overview integrity tiles have no data. Their screens can be built against fixtures; they cannot ship. |
| B2 | No staff roles: `users.role` is `user` or `admin` | `platform` + Mike | Every staff member is a full admin. Masking by role and the consent role cannot be enforced. |
| B3 | Consent method (email-plus vs a stronger 312.5(b) method) is with counsel (ADR 0001) | Mike + counsel | Whether the queue has a "needs review" lane with evidence depends on it. Designed both ways in `03-direction.md`. |
| B4 | `apps/admin-vite` has no `@acme/ui` dependency and no react-native-web / `react-native-css` pipeline (repo: `apps/admin-vite/package.json`) | `platform` | No kit component renders in the admin until the Vite pipeline matches `apps/storybook`'s. |
| B5 | Parent-rights deadline (312.6) and retention period for deletion receipts are not set | counsel | The "due by" column and its copy stay out of the build until counsel sets the number. |
